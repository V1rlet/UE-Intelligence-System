# Personal Codex Engineering Constitution

These defaults apply across repositories and to every tool, editor, service, adapter, data pipeline, automation, and UI that Codex helps build. Repository-specific `AGENTS.md` files may add stricter local constraints.

## Evolution, compatibility, and decoupling

1. **Introduce new capabilities with an old-content plan.** Before implementing a new model, tool, field, entry point, or workflow, identify existing data, APIs, user paths, and downstream consumers. Design the migration and rollback/exit path first.
2. **Centralize compatibility.** Old data must enter the runtime through a versioned migration or normalization boundary. Do not scatter legacy checks, guessed defaults, or temporary field mappings across UI components and business call sites.
3. **Version persisted formats explicitly.** Structural changes require an explicit format version plus deterministic, testable, preferably idempotent migrations. Never infer a version from filenames, dates, or incidental content.
4. **Converge instead of stacking systems.** When a new system replaces an old capability, migrate the old data and workflows onto shared domain services, then remove or demote the old entry point. Keep an old API only as a thin compatibility adapter with a stated reason.
5. **Depend on capabilities, not copied enums.** Tool availability, domain types, rendering, validation, and migration behavior should come from schemas, registries, adapters, plugin manifests, or capability declarations. Avoid hard-coded lists duplicated in pages.
6. **Use sliders first and numeric entry as the fallback for every continuous value.** Every adjustable continuous numeric parameter must expose both a slider and a validated, keyboard-editable numeric field. Drag gestures and shortcuts may supplement but never replace this pair. A slider may cover the common soft range; the numeric field must still allow precise values within the model's wider hard bounds.
7. **Do not invent semantics during migration.** Migrations may add structural defaults, but must not guess product, level, narrative, business, or user intent. Emit diagnostics and provide an explicit review path when lossless migration is impossible.
8. **Treat cleanup as part of delivery.** A feature is not complete while incompatible duplicate editors, dead entry points, or unexplained compatibility branches remain. Report what was replaced, removed, or intentionally retained.
9. **Define new-tool boundaries before integration.** State what data the tool owns, which domain services it reuses, which stable protocol it exposes, and how it can be replaced. Do not couple tools by directly reaching into one another's internal state.
10. **Verify old and new paths.** Completion requires fixtures from the previous format, migration to the current schema, edit/save/reload round trips, conflict protection, and current-format tests/builds.
11. **Give each fact exactly one owner.** Relationships, connectivity, identity, and state need one canonical source. Every 2D, 3D, list, hover, and export view must consume the same resolver; cached coordinates, presentation paths, and temporary UI state must not become competing facts alongside stable IDs.

When a request would make migration destructive or compatibility impossible, surface the tradeoff before proceeding unless the user has explicitly chosen the breaking change.

## Visible browser launch policy on Windows

When the user explicitly asks to open a URL in their visible default desktop browser, invoke `G:\UnrealProject\Tools\AgentBrowser\Open-AgentUrl.ps1 -Url <absolute-http-or-https-url>`. Do not use `Start-Process <url>`, `cmd /c start`, `--new-window`, or a separate browser profile for that action. The launcher must preserve the system default-browser association, reuse an existing Chromium instance as a new tab, and restore/maximize its foremost window. Browser automation and verification still use the applicable browser skill instead of this visible-launch helper.
